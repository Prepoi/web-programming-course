# L4. Гайд: общие правила и путь действия

[Задание A4](../README.md) · [Краткая справка](CHEATSHEET.md) · [Интерактивная модель](interactive.html) · [Слайды](slides-standalone/slides.html)

## От знакомого экрана к общей проблеме

В текстовом редакторе документ можно переименовать из списка и из открытого редактора. Если одно место разрешает пустое имя, а другое его запрещает, программа ведёт себя непоследовательно. Если оба места содержат собственные копии проверки, изменение правила придётся повторить несколько раз — и одну копию легко забыть.

Это не особенность React и не только проблема веба. В настольной программе команду можно вызвать через меню или горячую клавишу. На телефоне действие может начинаться с другого экрана, а данные — храниться иначе. В обеих версиях правила имени документа остаются теми же. Программе нужно распределить обязанности так, чтобы части могли передавать действие общему правилу и получать его результат.

В L3 мы разобрали состояние и формы: где живут ответы, кто ими владеет, как неизменяемо обновлять данные и как вычислять прогресс. Теперь вопрос следующий: как организовать правила, которыми пользуются несколько частей интерфейса, и как связать эти правила с вводом, отображением и внешними операциями? Такое распределение обязанностей и способов взаимодействия частей называют архитектурой приложения.

## Три обязанности

Полезно начать с трёх простых вопросов.

- Что получает ввод и показывает результат? Это работа интерфейса.
- Как программа решает, допустимо ли действие и каким станет состояние? Это работа правил.
- Как программа обращается к файлу, браузерному хранилищу или серверу? Это внешняя операция.

Владелец общего состояния связывает эти части. Он принимает сообщение интерфейса, применяет правило к данным и передаёт новое состояние обратно для отображения. Отдельная операция может сохранить выбранные данные во внешней системе и вернуть успех или ошибку.

Это не обязательное дерево каталогов или единственный способ разложить файлы. В небольшом приложении несколько обязанностей могут находиться рядом. Важно, чтобы было понятно, кто принимает решение, кто показывает его результат и кто разговаривает с внешней средой.

## Правило как функция над данными

Правило проще понимать, когда ему передают только значения, нужные для решения. Например, проверка имени документа не должна читать поле формы сама. Она получает строку и ограничение и возвращает результат.

```ts
type NameCheck =
  | { ok: true; name: string }
  | { ok: false; reason: "empty" | "too-long" };

function checkDocumentName(value: string, limit: number): NameCheck {
  const name = value.trim();

  if (name.length === 0) return { ok: false, reason: "empty" };
  if (name.length > limit) return { ok: false, reason: "too-long" };
  return { ok: true, name };
}
```

`NameCheck` описывает только проверку строки: при успехе возвращается очищенное имя, при отказе — причина `empty` или `too-long`. Например, ` План ` при пределе 10 даёт `{ ok: true, name: "План" }`, а `Планы недели` — `{ ok: false, reason: "too-long" }`. Функция не знает, было ли имя введено в списке или в редакторе. При одинаковых аргументах она возвращает одинаковый результат. Её можно вызвать без React, DOM и браузерного хранилища.

Когда правило меняет объект или коллекцию, старые данные не следует изменять на месте. Возвращайте новые значения только для изменённых частей. Это сохраняет ясную связь: было такое состояние, произошло такое действие, стало вот такое состояние.

Чистая функция не значит, что всё приложение должно избегать ввода-вывода. Форма должна принять текст, интерфейс — показать его, а команда сохранения — обратиться к хранилищу. Чистота относится к правилу: оно не читает DOM, часы, случайные числа, файл или сеть, пока принимает решение над переданными данными.

## Как части договариваются

Проверка имени и изменение списка документов — два разных шага. `checkDocumentName(value, limit)` получает строку и предел длины и возвращает `NameCheck`. Функция `renameDocument(documents, id, proposedName)` получает текущую коллекцию, идентификатор и новое имя; внутри использует `NameCheck`, а наружу возвращает итог изменения коллекции — `RenameResult`.

Для `RenameResult` в модели приложения смысл успеха — новый массив документов; смысл отказа — сообщение, а исходный массив остаётся прежним:

```ts
type DocumentRecord = { id: string; name: string; body: string };

type RenameResult =
  | { ok: true; documents: DocumentRecord[] }
  | { ok: false; message: string };
```

Например, если документ найден и имя прошло проверку, функция возвращает новую коллекцию с изменённым документом. Если имя пустое или слишком длинное либо `id` не найден, она возвращает сообщение и не меняет коллекцию. `NameCheck.reason` нужен самой проверке; `RenameResult.message` описывает отказ всего перехода. Это разные результаты разных функций, а не два варианта одного типа.

После проверки `ok` вызывающая часть знает, что у неё есть: новый массив или текст сообщения. Это небольшой контракт между правилом и владельцем состояния; он не диктует число компонентов или файлов.

В React дочерний компонент обычно получает значения через `props`, а о действии сообщает через callback. Например, список может получить документы и функцию `onRename`. Он не обязан знать, где лежит общее состояние или как устроена проверка имени. Открытый редактор может передать те же `id` и `name` в тот же callback.

## Общие данные и местные детали

Сам документ нужен и списку, и редактору, поэтому в приложении должна оставаться одна актуальная версия его имени и текста. Если каждый экран держит копию документа, после изменения одной копии вторая может показать старое значение.

При этом не каждое значение нужно поднимать к общему владельцу. Открытое ли меню, какая вкладка выбрана и какой текст ещё не отправили кнопкой «Переименовать» — детали конкретного участка интерфейса. Пока они не влияют на другие части приложения, могут оставаться рядом с этим участком.

Задайте себе два вопроса: кто ещё должен увидеть это значение и какое правило его меняет? Если несколько экранов читают один документ, им нужна общая модель. Если значение нужно только для раскрытого меню, отдельная локальная копия состояния может быть проще.

## Reducer и React

В L3 мы уже меняли состояние React через обработчики событий. Когда связанных переходов становится много, их удобно собрать в reducer. `useReducer` возвращает текущее состояние и `dispatch`; вызов `dispatch` сообщает, какое действие произошло.

```tsx
import { useReducer } from "react";

type CounterAction = { type: "increment" } | { type: "decrement" };

function counterReducer(count: number, action: CounterAction): number {
  switch (action.type) {
    case "increment": return count + 1;
    case "decrement": return count - 1;
  }
}

function Counter() {
  const [count, dispatch] = useReducer(counterReducer, 0);

  return (
    <div>
      <button type="button" onClick={() => dispatch({ type: "decrement" })}>−</button>
      <output>{count}</output>
      <button type="button" onClick={() => dispatch({ type: "increment" })}>+</button>
    </div>
  );
}
```

Здесь reducer решает только, каким станет счётчик. Он не рисует кнопку и не записывает значение в файл. Интерфейс может отправить одинаковое действие из разных мест; правило остаётся одним.

В тренажёре из A3 уже есть владелец попытки и устойчивые `taskId`. В A4 обзор и карточка могут сообщить об очистке ответа одного задания. Обе части должны передать один и тот же смысл действия владельцу общей попытки. Конкретную форму действий и компонентов каждый студент выбирает самостоятельно.

`useReducer` рекомендован, если переходы удобнее видеть в одном месте. Допустимо оставить `useState`, если изменения выражены чистыми типизированными функциями, которые принимают данные и возвращают результат. A4 проверяет поведение и ясность правил, а не выбор одного хука.

## Пользовательское действие и внешний мир

Не каждое изменение состояния требует эффекта. Если пользователь нажал «Сохранить», программа знает, что он попросил сделать, поэтому саму операцию обычно запускают из обработчика:

```tsx
type SaveResult = { ok: true } | { ok: false; message: string };

function handleSave() {
  const result: SaveResult = saveDocument(activeDocument);
  setStatus(result.ok ? "saved" : result.message);
}
```

Для локального хранилища эта операция синхронна. Код, который вызывает `localStorage`, перехватывает возможный отказ браузера и возвращает `{ ok: false, message }`. Редактор и введённый текст остаются на экране; отказ записи не отменяет сделанный ввод.

`useEffect` нужен, когда требуется синхронизировать React с системой вне React после изменения данных. Например, React может обновлять заголовок вкладки браузера:

```tsx
useEffect(() => {
  window.document.title = activeDocument.name;
}, [activeDocument.name]);
```

После первого появления компонента React запускает эффект и устанавливает заголовок для начального `activeDocument.name`. Затем React запускает его снова после рендера, когда значение в массиве зависимостей изменилось по сравнению с предыдущим рендером. Если имя не менялось, этот эффект повторно не запускается. Так DOM браузера синхронизируется с текущим документом. Эффект не является общим местом для любых действий пользователя. Если значение можно вычислить из props и state, обычно вычисляйте его при рендере; если пользователь явно нажал кнопку, обработчик уже знает, какое действие нужно выполнить.

TypeScript помогает проверить вызовы внутри программы во время разработки. Но типовая аннотация не проверяет содержимое, полученное из внешней системы во время выполнения. Когда приложение прочитает JSON или получит ответ API, формат нужно проверить отдельно — к этому мы вернёмся в L5.

## Замена одной внешней реализации

Внешнюю операцию удобно вызывать через понятный ей контракт. В локальном примере функция получает документ и сразу возвращает типизированный `SaveResult`: успех или отказ с сообщением. Одна реализация может записать значение в браузерное хранилище, другая — вернуть отказ. Компонент показывает результат и сохраняет ввод независимо от него.

Если меняется сама природа операции, меняется и взаимодействие с ней. Запись в локальное хранилище возвращает результат синхронно, а HTTP-запрос требует ждать ответ, показывать состояние запроса и проверять HTTP-статус. Для него обработчик и контракт придётся изменить; в L5 разберём этот путь отдельно.

## Context и библиотеки состояния

`Context` помогает передать данные или `dispatch` через дерево компонентов, когда обычные props пришлось бы проводить через много промежуточных уровней. Context сам по себе не хранит и не меняет состояние. Владельцем остаётся компонент или другой инструмент, который управляет значениями; Context только предоставляет их потребителям.

Redux предлагает общий подход к состоянию и переходам вокруг reducer. Zustand тоже помогает организовать общее состояние, но использует другой API и не является полной копией Redux. Для небольшой части приложения может хватить `useState` или `useReducer`.

В проектах также встречаются redux-persist для сохранения состояния Redux и Zod для проверки внешних данных. Это названия возможных инструментов, не обязательные зависимости курса. Сначала важно различать саму задачу и библиотеку, которая помогает с ней.

## Связь с A4 и L5

В A4 продолжается работа с попыткой из A3. До завершения пользователь может открыть обзор всех ответов. Ответ можно изменить в карточке задания; очистить его можно и из карточки, и из обзора. Оба способа очистки должны обновлять одни и те же ответы, прогресс и список пропусков. После `submitted` интерфейс закрывает изменение, а правило обработки действий оставляет завершённую попытку неизменной.

Сохраните `Answer` и стабильную связь ответа с `taskId`. Правила изменения и завершения должны принимать данные и возвращать результат, который можно проверить отдельно от рендера. Для реализации можно выбрать `useReducer` или `useState` с такими функциями. Не требуется внедрять Context, библиотеку, автотесты, слои файлов или восстановление после перезапуска.

В L5 появится другая программа — сервер. HTTP описывает способ обменяться сообщениями с ней, но сам по себе не является хранилищем. Клиенту нужно сохранить `attemptId`, затем запросить по нему подтверждённый `Attempt`. Если идентификатора нет или сервер больше не находит попытку, клиент не может заявить, что восстановил её. Отдельное сохранение неподтверждённого ввода не становится обязательным только из-за этой серверной связи.
